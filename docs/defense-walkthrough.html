2 · The system in one page

Four architectural rules (say them in this order)

  1. Events, not calls. No service calls another service's API. Coupling is only on the shared Kafka contract in the root README.
  2. Database per service. Each service owns its data; others keep their own read models built from events (CQRS style). If one service is down, the others still answer from their copy.
  3. Keyed by orderId. All events for one order land on one partition, so they stay in order; different orders spread over 3 partitions for parallelism.
  4. At-least-once, idempotent consumers. Kafka can redeliver, so every handler is safe to run twice (upserts, unique indexes, status guards).

Say: "Notice the Order Service is on both ends of the contract: it produces the two topics almost every service listens to, and it consumes the three topics that report progress back. That's why it is the centre of the choreography — but it still never calls anyone."

3 · My part: the Order Service

Ballerina 2201.13.5MongoDBKafkaport 8081

Responsibilities

  • Create orders (POST /orders): validate, compute the total, save as CREATED, publish orders.created.
  • Own the lifecycle: the only service allowed to change an order's status, and only along legal transitions.
  • Auto-advance orders from restaurant.status, payments.completed and delivery.status_updated.
  • Announce every change on orders.status_updated — which is what triggers refunds, delivery cancellation, notifications and admin stats elsewhere.
  • Serve queries for the customer's "My orders" page and the restaurant's kitchen board.

Module layout — one responsibility per module

Arrows = "depends on". Nothing depends on service.bal; lifecycle depends on nothing.

Say: "I split the service into Ballerina submodules with one-way dependencies. The key one is lifecycle: it holds the order types, the transition rules, total calculation and validation, and it imports nothing — no HTTP, no Kafka, no Mongo. That means the most important rules in the system can be unit-tested in under a second with no infrastructure running, and both the REST API and the Kafka consumer use exactly the same rules."

Why submodules and not just folders?

Ballerina only compiles .bal files sitting directly in a module directory — arbitrary subfolders are silently ignored. So the "folders" are real modules (modules/<name>/), which also gives us enforced boundaries: store cannot accidentally import messaging.

One non-obvious detail worth mentioning

service.bal calls messaging:consumedTopics() for the health endpoint. Besides reporting what we consume, it guarantees the module is imported — in Ballerina an unimported module's Kafka listener never starts.

4 · The order state machine

FromAllowed nextWho / what triggers it
CREATEDCONFIRMED, CANCELLEDrestaurant.status ACKNOWLEDGED / REJECTED, or customer cancel
CONFIRMEDPREPARING, CANCELLEDpayments.completed SUCCESS (or the ACK if payment came first)
PREPARINGREADY, CANCELLEDRestaurant clicks Mark ready → PUT /orders/{id}/status
READYOUT_FOR_DELIVERYdelivery.status_updated PICKED_UP
OUT_FOR_DELIVERYDELIVEREDdelivery.status_updated DELIVERED
DELIVERED / CANCELLED— (terminal)Every further request gets 409 Conflict

How it is enforced

One function, isValidTransition(current, next) in modules/lifecycle/types.bal:55, is a match on the current status. It is the single source of truth: the REST endpoint checks it before writing, and the Kafka consumer only ever asks for legal steps.

Say: "The state machine is deliberately strict. You can't skip steps, you can't go backwards, and terminal states stay terminal. Cancellation is only allowed up to PREPARING — once the food is ready we can't un-cook it, and once it's with the driver the delivery service also refuses to cancel. Every illegal request gets a 409, not a silent overwrite."

Catch-up behaviour

If the driver marks an order DELIVERED without a separate pick-up (order still READY), the consumer walks it READY → OUT_FOR_DELIVERY → DELIVERED using two legal transitions, so the history and the published events stay correct (consumer.bal:154).

5 · Event choreography: how orders move on their own

The hardest design problem in my service: the restaurant's acknowledgement and the payment result are produced by two different services on two different topics, so they can arrive in either order.

The rule: "whichever event arrives second advances the order"

  • Payment handler (consumer.bal:67) always stores paymentStatus on the order. If the order is already CONFIRMED and payment succeeded → advance to PREPARING. If still CREATED → do nothing; the ACK will finish the job.
  • Restaurant handler (consumer.bal:92) moves CREATED → CONFIRMED, then checks the stored paymentStatus; if it is already SUCCESS it continues straight to PREPARING.
  • A FAILED payment is recorded but the order stays put — the UI shows Retry payment, and a later SUCCESS advances it normally.

Rejection path (cancel + refund without any direct call)

restaurant.status REJECTED (reason: "closed" / "out of stock")
   └─ Order: store cancellationReason, CREATED|CONFIRMED → CANCELLED
        └─ orders.status_updated CANCELLED
             ├─ Payment:  refund any SUCCESS payment, remember order as cancelled
             ├─ Delivery: cancel delivery if not yet picked up
             └─ Notification / Admin / Customer: update their read models
Say: "My service doesn't know refunds exist. It just publishes 'this order is now CANCELLED', and the payment and delivery services each decide what that means for them. That's choreography rather than orchestration — adding a new reaction to cancellation needs zero changes in my code."

6 · Data design & consistency guarantees

The orders document

{
  "orderId": "uuid",          // unique index
  "customerId": "uuid",
  "restaurantId": "uuid",
  "items": [{ "itemId", "name",
              "quantity", "unitPrice" }],
  "totalAmount": 90.00,       // decimal
  "status": "PREPARING",
  "paymentStatus": "SUCCESS", // optional
  "cancellationReason": "...",// optional
  "createdAt": "ISO-8601",
  "updatedAt": "ISO-8601"
}

Design decisions

  • Items embedded as a snapshot of name and price at order time — if the restaurant changes its prices later, past orders don't change, and reading an order needs no join.
  • decimal, not float, for money.
  • IDs, not foreign keys — customerId / restaurantId live in other services' databases.
  • Optional fields (paymentStatus?) so documents written before a field existed still deserialise.

Indexes (created at startup, store.bal:31)

  • {orderId:1} unique — the platform-wide key
  • {customerId:1, createdAt:-1} — "My orders", newest first
  • {restaurantId:1, createdAt:-1} — kitchen board

Five guarantees and how each one is achieved

GuaranteeMechanism
No lost updates under concurrencyOptimistic concurrency. applyStatusTransition updates with filter {orderId, status: previousStatus}. If a REST call and a Kafka event race, only one matches; the loser gets matchedCount == 0 → an error / 409 instead of overwriting (store.bal:77).
Per-order orderingEvery event keyed by orderId → same partition → processed in order.
Redelivery is harmless (idempotency)Each handler checks the current status first: an ACK for an order that is no longer CREATED, or a pickup for an order that isn't READY, is logged and skipped.
No silent message loss on consumeautoCommit: false; offsets committed only after the batch has been handled (consumer.bal:22–42).
Durable publishProducer uses acks: "all" with retryCount: 3 (producer.bal:13).
Say: "Kafka gives us at-least-once delivery, so I designed every handler on the assumption that it will see the same event twice. The status check at the top of each handler plus the optimistic update in Mongo means replaying the whole topic from the beginning would leave every order exactly where it is."
Own it: a record that fails to parse is logged and its offset is still committed, so it is effectively dropped. That keeps one bad message from blocking the partition, but in production I'd route it to a dead-letter topic instead.

/health is its own service base path so it can never be mistaken for an orderId.

Validation rules (validateCreateOrder, types.bal:89)

  • customerId and restaurantId must be non-blank.
  • At least one item; each item needs an itemId and a name.
  • Quantity between 1 and 50 (MAX_ITEM_QUANTITY).
  • Unit price strictly greater than zero.
  • The total is computed on the server (computeOrderTotal) — the client never sends an amount, so it can't under-pay.

Ballerina also rejects malformed JSON or unknown status values automatically, because request bodies bind to closed records and the OrderStatus enum.

What the Order Service deliberately does not validate

It does not check that the restaurant is open or the dish is in stock — that data belongs to the Restaurant Service. Instead the order is accepted as CREATED and the restaurant answers asynchronously with ACKNOWLEDGED or REJECTED. This keeps services decoupled: placing an order works even if the restaurant service is briefly down; the order simply waits in CREATED until it recovers.

Say: "Validation is split by ownership. I validate what my service knows — shape, quantities, prices. Business rules about the restaurant are validated by the restaurant, and come back as an event. That's the price of not having synchronous calls, and it's also what makes the system resilient."

Three tiers, from fastest to most realistic.

Say: "The expected values in the transition matrix were written from the state diagram, not copied from the code — so the test actually checks the logic instead of restating it. Testing all 49 pairs means every 'not allowed' case is proven, not just the happy path."

Why the domain module made this possible

The store and messaging modules connect to Mongo and Kafka the moment they initialise, so anything importing them needs infrastructure. Putting the rules in lifecycle with zero I/O imports means the most important tests run anywhere, in well under a second.

11 · Expected questions & answers

About the Order Service (most likely)

What happens if the payment arrives before the restaurant acknowledges?
The payment handler stores paymentStatus = SUCCESS but leaves the order in CREATED. When the ACK arrives, the restaurant handler moves it to CONFIRMED and, seeing the stored SUCCESS, straight on to PREPARING. Either order of arrival ends in the same state.
What if a REST status update and a Kafka event change the same order at the same moment?
Both use applyStatusTransition, which updates with filter {orderId, status: expectedPrevious}. Mongo's single-document update is atomic, so only one matches. The REST caller gets 409 "changed concurrently, please retry"; the consumer logs the error. No write is lost or overwritten.
What if Kafka delivers the same event twice?
Each handler checks the current status first. A second ACK finds the order no longer CREATED and is skipped; a second pickup finds it no longer READY. The optimistic filter is a second safety net. So handlers are idempotent.
Why not have the Order Service call Payment and Restaurant directly (orchestration)?
Direct calls would couple availability — if Payment is down, nobody can order. With events, I publish once and each service reacts when it can; new reactions (notifications, admin stats) were added with no change to my code. The trade-off is eventual consistency and harder tracing, which we accept and mitigate with the health page and logs.
Why MongoDB for orders?
An order is a self-contained aggregate — header plus embedded items — always read and written as one unit. A document fits naturally, single-document updates are atomic (which my optimistic concurrency relies on), and there are no cross-entity joins. Payments chose Postgres because money needs constraints and ACID across rows.
Why are items copied into the order instead of referenced?
An order is a historical record. If the restaurant changes a price or deletes a dish, past orders must still show what the customer paid. It also avoids a cross-service lookup.
Why can't a READY order be cancelled?
The food has been made and the driver may be on the way; cancelling would waste food and conflict with the delivery service, which also refuses to cancel after pickup. It's a business rule encoded in isValidTransition.
How do you guarantee events for one order are processed in order?
All topics are keyed by orderId, so Kafka puts every event for that order on the same partition, and a partition is consumed in order. Across topics there's no ordering guarantee — which is exactly why I handle ACK/payment in either order.
What if your service crashes after saving the order but before publishing?
That's the dual-write problem: the order exists in Mongo but no one hears about it, and the customer gets a 500. The proper fix is a transactional outbox — write the event into an outbox collection in the same write as the order, and have a relay publish it. It's documented as a known limitation.
What does an unknown orderId in an incoming event mean?
Normally impossible, because I only publish orders.created after the save succeeds. If it happens (e.g. test data) it's logged as a warning and skipped, so it can't crash the consumer.
How would you scale the Order Service?
Run more instances in the same consumer group — Kafka spreads the 3 partitions across them, and per-order ordering is preserved because one order is always on one partition. The REST side is stateless, and the optimistic concurrency keeps instances from clobbering each other. Beyond 3 consumers we'd add partitions.

About the system as a whole

How does a cancelled order get refunded?
I publish orders.status_updated with CANCELLED. The Payment Service flips the SUCCESS row to REFUNDED and publishes payments.completed REFUNDED; it also records the order in cancelled_orders so a late charge can never go through.
Can a customer be charged twice?
No — Payment has a partial unique index allowing at most one SUCCESS row per order, enforced by Postgres even if two attempts race past the code check.
Can a driver get two deliveries at once?
No — Delivery claims a driver with filter {driverId, status: AVAILABLE}, the same optimistic pattern I use for orders. Only one claim can match.
Can stock go negative?
No — Restaurant decrements with {stockCount: {$gte: quantity}} plus $inc in one atomic update.
Why one MongoDB server if it's "database per service"?
It's one server for convenience in Compose, but each service has its own logical database and never touches another's. Moving one to its own server only changes Config.toml.
How do services stay compatible as events evolve?
One documented contract in the README, and consumers use open records, so a producer can add fields without breaking anyone. Removing or renaming a field would need a versioned topic.
How do you know the whole thing works?
The smoke test drives a real order through all seven services through the same nginx proxy the UI uses, including the rejection/refund path, and exits non-zero on any failure.
